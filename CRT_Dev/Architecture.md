# Cowfee Raid Tools: architecture

How the addon is put together, so a new feature or a patch fix can be made without re-reading every file. Start from [[Cowfee Raid Tools - readme]]. Build steps and patch checks are in [[Cowfee Raid Tools - Build and Patch Runbook]].

## Files and load order

**Folders.** The `.toc`, the docs and the packaging files sit at the top; everything else is in five folders. `CRT_Core/` holds what every feature uses (`Core.lua`, `Profiles.lua`, `Slash.lua`, `Perf.lua`, `UI/`, `Sound/`, `Integrations/`). `CRT_Modules/` holds one folder per feature. `CRT_Data/` holds the boss library (`Bosses/`) and the season packs (`Seasons/<season>/`: `Season.lua`, a file per boss, and a file per season topic that isn't a boss, each a `CRT.Bosses:SeasonData(season, topic, data)` call read through its own accessor, today `GearChecks.lua` and `Bosses:GearChecks()`). `CRT_Media/` holds the textures (`Media/`), the old user-sound folder (`Sounds/`) and the companion addon template (`Media Addon Template/`). `CRT_Dev/` holds the developer tools (`Dev/`, in the `.toc`'s do-not-package block) and the test suite (`Tests/`); `.pkgmeta` leaves all of `CRT_Dev` out of the release. Texture paths start from `CRT.MEDIA` (`Interface\AddOns\<ADDON>\CRT_Media\Media\`, set once in `CRT_Core/Core.lua`; each user keeps a local fallback for test harnesses that load it without `Core.lua`). Code comments name a file from inside its CRT_ folder (`Alerts/Areas.lua`).

Files load in the order the `.toc` lists them. Each file starts with `local ADDON, CRT = ...`, which gives every file the same private table. `CRT_Core/Core.lua` also exposes it as the global `CRT` for debugging.

| Order | File | Job |
|---|---|---|
| 1 | `CRT_Core/Core.lua` | Creates `CRT`, the default settings, the `CRTDB` saved variable, `CRT:Print`, and the scaled font objects |
| 1b | `CRT_Core/Themes.lua` | The themes, their palettes and `CRT.PALETTE`, the palette in use |
| 1c | `CRT_Core/Gear.lua` | The gear engine, `CRT.Gear`: your equipped gear, other players' gear, the wire format and the tooltip |
| 2 | `CRT_Core/Slash.lua` | The `/crt` command |
| 3 | `CRT_Core/UI/Panel.lua` | The main window, the left menu and the page registry |
| 4 | `CRT_Modules/Groups/Data.lua` | Names, rosters, roles, the working grid, saved layouts, export and import |
| 5 | `CRT_Modules/Groups/Apply.lua` | Moves the live raid into the grid's layout |
| 6 | `CRT_Modules/Groups/Page.lua` | The Raid Groups page: grid, picker, dialogs, Quick Load list, buttons |

`CowfeeRaidTools.toc` holds the title, version, `## Interface:` number and `## SavedVariables: CRTDB`.

## Saved data (`CRTDB`)

```lua
CRTDB = {
    window = { point, x, y },        -- panel position
    lastPage = "groups",             -- page key reopened by /crt
    classCache = { ["name-realm"] = "WARRIOR" },   -- last class seen, lowercase keys
    roleCache  = { ["name-realm"] = "TANK" },      -- last role seen, lowercase keys
    groups = {
        presets = { { id = 1, name = "Mythic Roster", slots = { 40 strings } } },
        nextId = 2,
        selected = 1,                -- id of the loaded layout, or nil
        keepChanges = true,          -- auto-save edits to the selected layout
        source = "raid",             -- name picker source: "raid" or "guild"
        working = { 40 strings },    -- the grid being edited
    },
}
```

A slot holds `"Name-Realm"` or `""`. Slot number is `(group - 1) * 5 + position`, so slots 1 to 5 are Group 1. Defaults are merged into the saved table on load by `copyDefaults` in `CRT_Core/Core.lua`, so adding a new setting only needs a new default.

## Names

Every stored name is `Name-Realm`, so same-name players on different realms stay distinct. `Groups.Normalize` appends your own realm to a bare name. `Groups.Display` uses `Ambiguate(key, "none")`, which hides the realm when it is your own. Comparisons use lowercase keys.

A name pasted without a realm is stored with your realm. `Groups.MakeLookup` (grid) and `resolveLayout` (apply) both fall back to matching the bare name against a raid member when the match is unique, so cross-realm players still match.

## Roles and class

`Groups:ReadRoster` returns `{ key, subgroup, class, role }` for each member. Raid uses `GetRaidRosterInfo`. Party and solo use `UnitFullName` and treat everyone as group 1, so you always appear in your own roster. Role comes from `UnitGroupRolesAssigned`, and your own role falls back to your spec. Every class and role seen is cached in `CRTDB` so absent players keep their color and icon.

## Panel and pages

`UI:RegisterPage(key, title, builder)` adds a menu entry. The panel builds each page lazily the first time it is selected and calls `builder(pageFrame)`. The page sets its own `OnShow` to refresh. `UI:Show(key)` and `UI:Toggle()` open the panel.

## The Raid Groups page

| Piece | How it works |
|---|---|
| Slots | 40 backdrop buttons. Left-click opens the picker, right-click clears, drag swaps |
| Drag and drop | A ghost frame follows the cursor and the drop target is found with `IsMouseOver`, because other frames get no mouse events during a drag |
| Picker | One shared popup with an edit box and 10 rows, plus a full-screen click catcher that closes it |
| Dialog | One shared frame for the one-line name prompt and the multi-line Export and Import box |
| Quick Load | A scroll list of saved layouts, rebuilt on every change |
| Rename | An edit box in the header, shown when a layout is loaded. It saves through `Groups:Rename` when it loses focus, and the refresh never overwrites it while it is being typed in |
| Refresh | Every edit calls `Groups:Fire()`, which refreshes the page. The page also refreshes on group, guild, role and spec events |

Edits go through `Groups:SetSlot`, `Swap` and `ReplaceWorking`. Each ends in `Groups:Touch()`, which marks the grid unsaved, auto-saves when Keep changes is on, and fires the refresh.

## Consumables

The ready check row is separate from the group layout code. `CRT_Modules/Consumables/Database.lua` is the list of consumables that ships with the addon. `CRT_Modules/Consumables/Data.lua` holds the categories, the player's saved order in `CRTDB.consumables`, bag helpers, and `Consumables:Status(key)`, which turns one category into an icon, a time, a count and a state (active, low, missing, unknown, unset).

`CRT_Modules/Consumables/Bar.lua` draws the icons, and is shared by the ready check row and the bar on the tab.

The tab lets the player drag items onto the bar to add their own entries (`CRTDB.consumables.extra`), and `Data.lua` learns the buff of an item the first time it is used, by watching its bag count drop and a new long buff appear (`CRTDB.consumables.learned`).

`CRT_Modules/Consumables/Ants.lua` is the marching ants animation, and `CRT_Modules/Consumables/Tools.lua` holds the `scan` and `check` maintainer commands. `CRT_Modules/Consumables/Display.lua` is the five-icon frame, shown on `READY_CHECK`, anchored to Blizzard's dialog when it can be found, and refreshed twice a second.

Food, flask and weapon icons are secure buttons that use the first assigned item in your bags, which makes the row protected, so showing, hiding, moving and changing the click action wait for the end of combat.

`CRT_Modules/Consumables/Page.lua` is the tab: the live bar, drag and drop, the icon order, and the item priority. The full detail, display rules and the update routine are in the maintenance skill's `references/consumables.md`.

## Previews and saved positions

`CRT_Core/UI/Panel.lua` has a preview registry. A floating panel calls `UI:RegisterPreview(key, setFn)`, and the **Previews** button in the corner of the main window calls every registered function, then turns them off again when the window closes. Each panel shows a drag handle during a preview and saves its position in `CRTDB` when dropped, in `CRTDB.consumables.position` and `CRTDB.debuffs.position`. All of this is saved per player in their own saved variables, and new settings are added as defaults in `CRT_Core/Core.lua`.

`CRT_Core/UI/Controls.lua` builds every dropdown and slider on the pages, in the style of the game's Edit Mode settings: `UI.Dropdown` uses `WowStyle1DropdownTemplate` with a radio menu (`SetupMenu`, `CreateRadio`, `GenerateMenu` on refresh), and `UI.Slider` uses `MinimalSliderWithSteppersTemplate` (`Init`, the `OnValueChanged`, `OnInteractStart` and `OnInteractEnd` callbacks, and a Right label formatter). Each returns a row frame with `refresh()`, so pages add it to their controls list. No page cycles through choices with a button.

`CRT_Core/UI/ScrollBar.lua` skins every scroll bar: call `UI:SkinScrollBar(bar)` right after making a `MinimalScrollBar` (pass the bar) or a `UIPanelScrollFrameTemplate` scroll frame (pass its `.ScrollBar`), or after giving a hand-made vertical `Slider` its track texture and thumb (the Pace list; pass the slider, whose own textures stay in Default: Blizzard). No row may run under its bar, in any theme: a scroll frame or scroll box clips its rows and keeps its bar `UI.SCROLL_GAP` right of it; a list that draws its bar inside itself, or beside rows it doesn't clip, ends its rows `UI.ScrollGutter(barWidth)` short of where the bar ends (the Mech Alerts list). `run_scrollbar.js` checks every list's rows against its bar in every theme. Each Modern theme names its look with `scrollBar` in `CRT.THEME_LIST` (`rail`, `framed` or `rounded`, sizes and palette keys in `UI.SCROLL_BAR_LOOKS`); Default: Blizzard, or a theme without one, keeps the game's art. The skin only hides the game's art and arrow buttons (alpha 0, mouse off) and draws over the track and thumb, so the game's wheel, drag and track click are untouched. The bar joins `UI.skinned`, so `UI:SetTheme` redraws it live. The suite's `scrollbar` group fails on a scroll bar made without it, made inline, made in XML, or from a scroll bar template the skin doesn't know yet, unless its `ALLOW` list names it with a reason (today only the Timeline's sideways bar).

`CRT_Core/UI/SettingsPage.lua` is the General Settings page (named Addon Settings before 0.16.0, key still `settings`), in three columns, saved in `CRTDB.ui` (and `CRTDB.window.scale`, which moved there from Quality of Life). Fonts: every addon text uses the `CRTFont*` objects made in `CRT_Core/Core.lua` (including `CRTFontEdit` for edit boxes, `CRTFontButtonSmall*` and `CRTFontStandard*` at the game's own sizes, and the dropdown and slider template text), and `CRT:ApplyFonts` sets their face, outline and size together. `CRT:FontList` is the game's four fonts plus any shared through LibSharedMedia-3.0 when another addon loaded it (read through `LibStub`, never shipped). Picking a font on Addon Settings asks first in the game's confirmation box, then `CRT:SetAddonFont` sets it for all text and every note window, which redraw through `Notes:Fire`. Fonts are applied again at `PLAYER_LOGIN`, once every addon has registered its shared fonts. Style: `UI:ApplyStyle` shows the `BasicFrameTemplateWithInset` textures in Classic and a flat `background` in Modern, and sets the window's opacity. Layers: each floating window calls `UI:RegisterLayer(key, frame)` instead of `SetFrameStrata`, with the kinds and defaults in `UI.LAYERS`; `UI:SetLayer` saves a change and applies it, and a protected frame (the consumables bar) waits until combat ends. The boss debuff timers keep the game's own font, because `Blizzard_PrivateAurasUI` draws them with the shared `GameFontNormalSmall` in a protected environment. Reports: `ui.hideRealms` makes `Groups.ReportName` (in `CRT_Modules/Groups/Data.lua`) drop realms with `Ambiguate(key, "short")`; the Late Tracker and Tattlebot use it for names on their pages, in chat posts and in Discord exports, while the Raid Groups grid keeps `Groups.Display`.

Since 0.16.0: **Profiles** (`CRT_Core/Profiles.lua`). A profile is every key in `CRT.defaults` except the shared `classCache` and `roleCache`. The active profile stays at the top of `CRTDB` under its old keys, the others wait in `CRTDB.profiles[name]`, and `CRTDB.activeProfile` and `CRTDB.defaultProfile` name them. Each character's choice is in the per-character saved variable `CRTDBChar.profile`. `Profiles:Load`, called from `CRT_Core/Core.lua` on `ADDON_LOADED` before the defaults are filled in, swaps the character's profile to the top, so switch, copy and reset only save the choice and call `ReloadUI`. Export is `C_EncodingUtil` CBOR, deflate and base64 behind a `CRTP1:` prefix.

**Minimap** (`CRT_Core/UI/Minimap.lua`): a draggable button at `CRTDB.minimap.angle`, hidden with `CRTDB.minimap.hide`, plus the global `CowfeeRaidTools_OnAddonCompartmentClick` named in the `.toc` for the game's addon menu.

**Reset position** (after 0.16.0): `UI.ResetButton(parent, onClick)` in `CRT_Core/UI/Panel.lua` is a small Reset button on each movable window. It sits on the drag bar of the consumables bar, debuff panel and your next spell alert, in the top right of a note window while it is unlocked, and in the top right of the ready check window and low-health banner during Previews. The pages no longer have Reset position buttons. `/crt dev reset` (developer builds only) resets every window and the main panel at once.

**Looks**: there are two, Classic and Modern, in four themes (`CRT_Core/Themes.lua`, loaded right after `Core.lua`): Default: Blizzard (`blizzard`, the Classic look), Blackout: Midnight (`midnight`), Blackout: Nitro (`nitro`) and Beanworks: Cowfee (`cowfee`). `CRT.THEME_LIST` is the menu's order, names and flags (`modern`; `menuBar`, the blackouts' 2 px accent bar left of the selected menu page), and `CRT.THEMES[key]` is each palette, with every key in `CRT.THEME_KEYS` (each named for what it colours: `background`, `surface`, `border`, `accent`, `text` and so on; the list is in `CRT_Dev/StyleGuide.md`). `CRT.PALETTE` is the theme in use: `CRT:UseTheme` refills its own colour tables, so every `CRT.PALETTE.x` read follows the theme, and nothing outside `Themes.lua` writes a palette colour (the suite's "old Modern colours" grep). `ui.theme` saves it and `ui.modern` is kept in step (`CRT:ResolveTheme`, which also maps data from before themes: modern on is `cowfee`, off is `blizzard`), so `UI:IsModern()` still answers Classic or Modern. The `UI.lookButton` header button in the main window's title bar shows the theme's name and opens the theme menu under it (`UI.ContextMenu` with an anchor, `UI:FillThemeMenu`); `UI:SetTheme` saves the pick and applies fonts and style live (`UI:SetModern` is a compatibility shim for on/off callers). Anything colored from `CRT.PALETTE` once, when it is made, uses `UI.Tint(region, setter, key, alpha)` (View.lua and RehearsalWindow.lua wrap it as `themed`), and a surface that reads `CRT.PALETTE` as it draws registers `UI:OnTheme(fn)` to redraw; `UI:RepaintTheme` runs both after a switch, then the page in view's OnShow refresh and any open window's `refresh`. `UI.ContextMenu(owner, fill, anchor)` opens at an anchor through the menu manager (`Menu.GetManager():OpenMenu`, as the game's dropdown buttons do) and falls back to the cursor menu moved there. Every theme has one heading, one good, one warn and one bad colour (`heading`, `good`, `warn`, `bad`; Default: Blizzard's are the game's gold, green, orange and red, read from `NORMAL_FONT_COLOR`, `GREEN_FONT_COLOR`, `ORANGE_FONT_COLOR` and `RED_FONT_COLOR` with fallbacks): `UI.GoodText(text)`, `UI.WarnText(text)`, `UI.BadText(text)` and `UI.HeadingText(text)` write markup in them, `UI.Color(key, alpha)` gives r, g, b, a for a setter, `UI.Hex(key)` the hex, and `UI.ThemedText(fontString, build)` sets a text built from them now and again after every switch. **`CRT_Dev/StyleGuide.md` is the one reference for themes**: every palette role and every theme's value, which helper to use, the colours that are not the theme's, and how to add a theme. The suite's "status and heading colours from the theme" grep keeps hard-coded reds, oranges, greens and gold out of `CRT_Modules` (tooltip lines keep the game's gold; a fixed colour says `not a theme colour` on its line). `UI:ApplyStyle` keeps the button's label and paints the window with `CRT.PALETTE`, `UI:LayoutMenu` groups the menu by `UI.MENU_GROUPS`, page tabs register with `UI:RegisterTab` and change through `UI:SetTabSelected`, and `UI:SkinTree` gives every `UIPanelButtonTemplate` button and `WowStyle1DropdownTemplate` dropdown a flat skin it can switch on and off (run when a page is built and when a tab changes), and every `UICheckButtonTemplate` checkbox `UI:SkinCheckButton`: in Modern a 16 px rounded box, `surface` with a `selected` edge when unticked and `knob` (`CRT.PALETTE.knob` and `knobShine`, shared with the slider knob) with a `checkBorder` edge and a `check` tick (`CRT_Media/Media/Check.tga`) when ticked, kept in step by hooks on `SetChecked`, `SetEnabled`, `Enable`, `Disable`, `PostClick` and the mouse. Radio buttons keep the game's look. Checkboxes made after the page is skinned (pooled list rows, the dev info box) call `UI:SkinCheckButton` themselves. `CRT:ApplyFonts` uses Arial Narrow at 110% when the font is Default, and turns the game's gold text the `label` colour and white text the `text` colour.

Sound: every sound the addon plays goes through `CRT:PlaySound(kit)` in `CRT_Core/Core.lua`, which uses the channel picked on Addon Settings (`ui.soundChannel`: Master, SFX, Dialog, Ambience or Music). `CRT_Modules/QoL/LowHealthSound.lua` turns on the game's own low-health pulse from Combat Audio Alerts (`CAAEnabled`, `CAAPulsePlayerHealthPercent` 1 to 9 for under 90% to under 10%, and `C_CombatAudioAlert.SetCategoryVolume` for its volume), because an addon can't compare your secret health to play a sound itself. It saves every game setting it changes in `qol.lowHealth.caaSaved` and puts them back when turned off, and switches off the spoken alerts only when Combat Audio Alerts were off before. The game plays the pulse on its own voice output, unless another Sound or Output is picked: then the game's pulse is set to volume 0 and a `hooksecurefunc` on `CombatAudioAlertManager:SetHealthPulseSoundKit` plays your choice with `C_Sound.PlaySoundWithOptions` on your channel whenever the game's pulse starts, changes tier or stops. **Work in progress since 0.14.1:** the low-health sound is switched off (`LowHealthSound.WIP`), because the game hides its low-health decision from addons and its Combat Audio Alerts code errored on health changes alongside other addons; the code is as in 0.14.0.

## Ready Check

`CRT_Modules/ReadyCheck/Page.lua` is the Ready Check settings page, with the tabs Window, Your bar and Settings (the automatic report, called On ready check before 0.13.1) (the Raid report tab was removed in 0.13.0, and checking the group now happens in the ready check window, where `Window:PostColumn` posts a shift-clicked column).

Your bar is built by `CRT_Modules/Consumables/Page.lua` through `CRT.ConsumablesPage.Build`, so the consumables code is unchanged apart from `Consumables:BuffIds`, which hands the report the buff IDs listed or learned for a category. Both lists on Your bar are reordered by dragging rows (`draggable` in `CRT_Modules/Consumables/Page.lua`, which calls `Consumables:MoveCategoryTo` and `Consumables:MoveItemTo`). The bar's on/off, Not when I start the ready check (`consumables.notStarter`, checked on `READY_CHECK` in `CRT_Modules/Consumables/Display.lua`) and the warning minutes are on the Settings tab. `CRT_Modules/ReadyCheck/Report.lua` reads every group member's buffs with `C_UnitAuras.GetAuraDataByIndex`, runs the food, flask, rune, Vantus rune and raid buff checks, and posts or prints the result. It also runs on `READY_CHECK` and `START_PLAYER_COUNTDOWN`, and posts to chat only for whoever started them. Players whose buffs come back secret are reported as couldn't check.

`CRT_Modules/ReadyCheck/BuffLock.lua` is the Ready button lock (`readycheck.buffLock`, on by default). On `READY_CHECK` it finds your class's raid buffs in `Report.BUFFS`, reads the group with `Report:ReadGroup` and `Report.Cell`, and if anyone readable is missing one it disables the game's `ReadyCheckFrameYesButton` and lays a cover button over it with a tooltip of who is missing what. The cover rechecks after `UNIT_AURA` (at most every 0.25 s, only while locked), unlocks when everyone has the buff, after 10 seconds, or on `READY_CHECK_FINISHED`. While Shift is held it enables the game's button and stops taking the mouse, so the click is the game's own and the addon never answers the ready check itself.

`CRT_Modules/ReadyCheck/Window.lua` is the ready check window, built on `Report:ReadGroup` and `Report.Cell`, with durability shared over the `CRTReady` addon message prefix. See the maintenance skill's `references/readycheck.md`.

## Debuffs

`CRT_Modules/Debuffs/Data.lua` holds the settings, `CRT_Modules/Debuffs/Panel.lua` builds the panel, and `CRT_Modules/Debuffs/Page.lua` is the settings tab. The panel is one Blizzard AuraContainer (`Blizzard_AuraContainer`, patch 12.1.0, loaded with `C_AddOns.LoadAddOn` before the first `CreateFrame("AuraContainer", ..., "CustomAuraContainerTemplate, DisableUntrustedLayoutScriptsTemplate")`) on the player's `HARMFUL` auras, one aura group sorted shortest first, with candidate filters from `Debuffs:CandidateFilters()`: `isFromPlayerOrPlayerPet = false`, `maxDuration` from the Hide debuffs longer than setting (`CRTDB.debuffs.maxDuration`, 300 by default, 0 off) and `excludeSpellIDs` from `Debuffs.EXCLUDED_SPELLS` (Exhaustion, Sated and other lockouts). The container fills buttons this addon builds (`initializeFrame` gets the button first) through the button API, each call with its options table: `SetIcon`, `SetDurationCooldown`, `SetDurationText` (with a numeric formatter), `SetApplicationCount` and `AddDispelTypeTexture` (style Icon, harmful only), and the matching `Clear` calls when a setting is off; it never hands the values to addon code, so it works in combat. The preview tiles are built from the same parts. Until the container, the panel was a row of private aura anchors (`C_UnitAuras.AddPrivateAuraAnchor`) plus an optional container row that never loaded its addon. The anchors are kept as an optional second row (`CRTDB.debuffs.privateSlots`, off by default) in case some boss mechanic debuffs are private and never reach the container; whether they do is the in-game check that decides whether the anchors can be retired. The panel is faded with alpha, not shown or hidden, so combat cannot block it, and the container stays shown and enabled. `/crt dev debuffs` (developer builds only, also a button in the `/crt dev` editor) reports whether the addon loaded, the container and its template, the filters, the live frame count and every failed call. See the maintenance skill's `references/debuffs.md`.

The Look settings (`swipe`, `swipeEdge`, `countdownNumbers`, `timerPosition`, `timerX`, `timerY`, `borderScale`) are passed straight into each anchor's arguments: `showCooldownFrame`, `showCooldownEdge`, `showCountdownNumbers`, `iconInfo.borderScale`, and `durationAnchor`, which is left out when the timer is hidden. `Debuffs:TimerAnchor` turns a position into anchor points. The anchors are rebuilt out of combat whenever any of these change, the preview tiles draw the same choices with a live Cooldown swipe, and the regular row's swipes follow them too.

## Raid notes

`CRT_Modules/Notes/Parse.lua` reads the note text into timers, phases, free text and an invite list. `CRT_Modules/Notes/Data.lua` stores notes in `CRTDB.notes`, caches spell names and icons out of combat, and turns an invite list into a Raid Groups layout. `CRT_Modules/Notes/Engine.lua` starts the timers on `ENCOUNTER_START` (or a test run), starts later phases on Next phase, and decides which lines are yours by name or role. `CRT_Modules/Notes/Window.lua` builds three windows from one design (timers, assignments, personal note), each lockable and resizable by hand, `CRT_Modules/Notes/Page.lua` is the Raid Notes page with five tabs (Notes, Reminders, Phases, Alerts, Settings), `CRT_Modules/Notes/Reminders.lua` and `CRT_Modules/Notes/Phases.lua` build the Reminders and Phases tabs, `CRT_Modules/Notes/AlertsTab.lua` builds the Alerts tab (where your note lines show, and each kind of alert's look), `CRT_Modules/Notes/Settings.lua` builds the Settings tab (the windows, your alert's timing and voice, and sharing), `CRT_Modules/Notes/Alert.lua` is the personal alert, and `CRT_Modules/Notes/Comm.lua` shares a note in parts over addon messages. See the maintenance skill's `references/notes.md`.

**The rendered note (2026-10-21).** The Note text and Personal note boxes on the Notes tab show the note as it reads in the game, from `CRT_Modules/Notes/Render.lua` (`CRT.NoteRender`); the raw text stays the saved source, so sharing, alerts and imports are unchanged. `Render.Rows(text, ctx)` reads the text with the note parser (`Parser.Parse`, plus `Parser.SplitLines` and `Parser.Field` for a line's `DisplayType`) into rows with no frames: a header (boss, difficulty, encounter ID, "roster linked"), the timers by phase and time (m:ss, a phase chip, the tags class coloured with "(you)" after your name, the line's `colors:` as a swatch, the spell's icon and name or "Spell <ID>" until the game loads it, then the display type), the lines the parser could not read as a timer (`note.unread`) as written, the other lines (a label line "Melee: names" with its names coloured, a line with no colon as a heading, blank lines), and the invite list folded to "Invite list (N)", opened by a click. The personal note also reads `# heading`, `---`, `- bullet` and `**bold**`. Class colours come from `Render.ClassLookup()`: the live group, then the guild roster (both skipped in combat), then names seen before (the shared class cache and the Loot Master session). `Render.View` draws the rows into a scroll frame from pooled row frames, once per change: the text, the invite list opened, a spell loaded, a theme switch (`UI:OnTheme`) or a roster change (drawn on the next refresh); a view off screen draws when it is next shown, and both views share one class lookup per change (`Render.SharedLookup`). A spell is asked for once (`C_Spell.RequestLoadSpellData`): `SPELL_DATA_LOAD_RESULT` with success draws once more, and a failed load, or a load that still gives no name, marks it failed, so it keeps showing "Spell <ID>" and is never asked again. The muted texts (the display type, the header's small line, the empty hint) are tinted `muted`. `Render.Bind` pairs a view with its raw edit box: a click on the view shows the raw text with the focus, Save or Escape with nothing typed shows it rendered again, and unsaved typing keeps the raw box until it is saved or another note is picked. For a raider who can't change the raid note (`Notes:CanEditRaid`) the raw text is read-only: it can be selected, `OnTextChanged` with `userInput` puts the loaded text back, and Save stays greyed.

Since the alerts engine, `CRT_Modules/Notes/Engine.lua` no longer keeps its own clock. It keeps its public calls (`Start`, `Stop`, `NextPhase`, `Remaining`, `CurrentPhase`, `Elapsed`, `IsMine` and the rest), so the windows and the page did not change, but its timers are the `note` block of the alerts engine and its phase starts come from the engine's clock. `NoteEngine:Start` hands the note to the engine unless the engine is already collecting a pull, `/crt note stop` stops the whole run, and text to speech moved to `CRT_Modules/Alerts/Speech.lua` (`NoteAlert:Speak` is now a wrapper). Nothing under `CRTDB.notes` was renamed.

**Where your note lines show.** `NoteEngine.ItemFor` builds a note line's outputs. For a line without `show:`: the Next spell alert follows `CRTDB.notes.alert.enabled`, the bar follows `alerts.bars.noteLines` (and the bars' Show switch), speech follows `CRTDB.notes.alert.tts`, and the text, icon and circle follow `CRT.db.alerts.noteLines = { text, icon, circle }` (all off until chosen, so a player who never opens the Alerts tab sees what they saw before). A line with `show:` keeps its own displays; each display's own switch can still turn it off. Speech and the sounds of note lines follow only the "Read them out" switch (`notes.alert.tts`), not the Next spell alert switch (ruling B2): `tts` is the master speech switch for every block, so turning it off also silences reminders. A save that had the alert off and speech on is told once at login, through the `alerts.speechNotice` flag (`Speech:SpeechNotice`), that its note lines are now read out.

**Note targets.** `CRT_Core/Integrations/NoteTargets.lua` (`CRT.NoteTargets`) is the list of other raid addons a CRT note can be sent to, each one file that registers itself with the same interface: `key`, `label`, `help`, `IsAvailable()` and `CanSend()` (each `ok, reason`), `Format(record)` (the addon's text and `{ encounterID, name }`), `Send(text, meta, done)`, `Clear(done)`, and optional `Current()`, `OnReceived(fn)` and `Samples`. `Targets:Share(key, record)` checks, formats, sends and says in chat how it went; a sender receives its own group messages, so `OnReceived` confirms the note arrived on this client, or after 30 seconds says it did not. Neither addon has a public send call, so each file speaks that addon's addon-message format, with every protocol constant in a `WIRE` table at its top, the one place to fix after an update of that addon; their code is never copied or changed. `CRT_Core/Integrations/NSRT.lua` sends to Northern Sky Raid Tools' shared reminder note through NSRT's own AceComm-3.0 (borrowed through `LibStub`, never shipped), and `NSRT.ToNSRTText` keeps the header only with an ID and a name, writes `tag:all` as `everyone` and a class as its class ID, and drops CRT-only fields and the invite list. `CRT_Core/Integrations/MRT.lua` sends to Method Raid Tools' note with `C_ChatInfo.SendAddonMessage` under `EXRTADD`, in parts of at most 220 bytes through one queue (in order, waiting a second on the throttle), then the note's boss and name; `MRT.ToMRTText` turns a timed line into `{time:M:SS}` (`,pN` after phase 1), `{spell:ID}`, the names and ` - text`, wrapped in `{T}`/`{H}`/`{D}`, `{gN}` or `{c:Class}` when the tag is only one role, groups or classes, `{everyone}` for all, and drops the header, the invite list and tabs. Share to raid on the Notes tab sends to the **Send to** dropdown's choice, saved in `CRTDB.notes.shareTarget`: CRT (the default, `CRT_Modules/Notes/Comm.lua`), a target (greyed out with the reason when its addon isn't loaded), or All available. `/crt dev nsrt` and `/crt dev mrt` (`send`, `clear`, `status`, `preview`, `samples`) and `/crt dev all send` (`CRT_Dev/Dev/NoteTargets.lua`, developer builds only) use the same code.

**Break timers across addons.** `CRT_Modules/QoL/BreakTimer.lua` owns the break (`/crt break`, addon prefix `CRTBreak1`, the end saved in `CRTDB.qol.breakTimer.endsAt`); `CRT_Core/Integrations/Breaks.lua` (`CRT.BreakFormats`) only speaks the other formats, with every external constant in its `WIRE` table: Northern Sky's `NSI_BREAK_TIMER` (and its sync request and sync, through NSRT's transport, now shared as `NSRT.Encode`, `Decode`, `SendRaw` and `Listen` in `CRT_Core/Integrations/NSRT.lua`), BigWigs' `P^Break^<seconds>` under `BigWigs`, and DBM's `BT` under `D5`. MRT has no break of its own: its Timers page sends the BigWigs and DBM messages. A shared CRT break or cancel is also sent in each format ticked under Also send to (`breakTimer.formats`, all on by default; BigWigs and DBM are sent even when not installed here). `Break:Receive(source, sender, seconds)` takes a break or a cancel (0) from the leader or an assistant in any format, never from yourself, and treats breaks ending within `DEDUPE` (3) seconds of each other as one. With Bridge on (`breakTimer.bridge`, off by default) the raid leader's CRT waits `BRIDGE_WAIT` (1.5) seconds to see which formats a break or cancel arrived in, then sends it once in the ticked formats it didn't, and as a CRT break. The leader's CRT also answers NSRT's sync request while a break runs. The settings are the Break timer tab of Quality of Life, and `/crt dev break send`, `cancel` and `status` (`CRT_Dev/Dev/Breaks.lua`, developer builds only) test the formats.

## Alerts

`CRT_Modules/Alerts/` is the engine behind the Raid Notes timers and your own reminders. `Rules.lua` is the conflict rules as plain functions with no game calls (constants `DUPLICATE`, `GROUP`, `SPEECH_BEHIND`, `SPEECH_TIMEOUT`), `Engine.lua` holds the blocks, the run and the one phase clock, `Speech.lua` is the speech queue, `Reminders.lua` saves reminders and works out their times, `PhaseDatabase.lua` is the shipped phase triggers (empty until the dev probe confirms one), `Phases.lua` watches the phase events, `Areas.lua` is the builder every alert area is made from, `Bars.lua`, `Texts.lua`, `Icons.lua` and `Circles.lua` are the four areas, `Draft.lua` is the alert draft and how it is saved as a reminder (no frames), `SpellLookup.lua` is the spell lookup by name that attaches to any edit box, and `Editor.lua` is the popout alert editor. The editor and the Mech Alerts panel (`CRT_Modules/Notes/Reminders.lua`) share Draft and SpellLookup. In `.toc` order, Rules, Engine and Speech load before the Notes files, and Reminders, PhaseDatabase, Phases, Areas, Bars, Texts, Icons, Circles and Editor load after the Timeline files, since reminders read the references.

**Blocks.** Everything on screen comes from a block, registered with `Alerts:RegisterBlock(key, { label, group, Entries })`. `Entries(run)` returns items with `ph` (the phase) and `time` (seconds into it). The blocks are `note` (`CRT_Modules/Notes/Engine.lua`, `group = false`, so a note's lines show exactly as before), `mine` (your reminders, `group = true`) and `minetest` (the editor's Test, which gives items only to a run with reason `test`). Blocks do not compete: duplicates (`DUPLICATE`) and grouping (`GROUP`) apply only inside one block with `group = true`. Speech is the one place that drops across blocks: when the queue falls behind, raid-wide lines are dropped first, your note lines are kept longer, and your reminders are kept longest.

**The run.** `ENCOUNTER_START` calls `Alerts:Start`, which runs the `onPull` hooks (the note engine picks its note, the phase watchers snapshot the boss units), collects every block's items once, then starts the lowest phase. `ENCOUNTER_END` stops a run that began on an encounter. A later phase starts on its event or on Next phase and a repeat is ignored. Starting a phase skips the earlier ones that never began. A phase with an event trigger is never the pull phase. `Alerts:Lines(now)` turns the started phases' items into timed lines through `Rules.Lines`, and the Next spell alert, the bars and the speech queue all read those lines. Items with no output (other players' note timers, which only show in the timers window) are left out, `Rules.Area` picks the lines for the text, icon and circle areas (those whose output is on, from `warn` seconds before they are due until `hold` seconds after, where `hold` is at least 0.5), `Rules.SpeechItems` builds an alert's spoken parts for both reminders and note lines, and the lines are built once per change: `Alerts.version` goes up on Start, Stop, StartPhase and RegisterBlock, and until then every caller gets the same table, which they only read. Next phase (the Notes page button, `/crt note next`) works for any run, with or without a note, and walks the merged phase list of every block; `Alerts:PeekNextPhase()` names the phase it would start without starting it, so the button reads `Next phase (1.5)` and the chat line says which phase started. A pull with reminders but no note shows on the Notes page as running reminders, while `NoteEngine.running` (the note windows) stays false. A note run replaced by another run, such as the editor's Test, drops its note.

**Reminders.** `CRT.db.alerts.reminders[encounterID][id]` holds a reminder with its text, spell, outputs (alert, bar, speech), warn, speech mode, priority, difficulty and optional typed `times` (`P1 0:02, 1:17; P2 +0:18`). With no typed times the times come from the boss's reference timeline, converted to a phase and seconds into it through the numbered phase lines. They are keyed by the encounter ID that `ENCOUNTER_START` gives, so the tabs list only bosses with one: recorded pulls, the current raid's bosses from `Journal:RaidBosses()` (shared with the Timeline page) and references with an Encounter line. The double-click on a cast in `CRT_Modules/Timeline/View.lua` opens the editor with the spell and time filled in (a reference row with no spell prefills the row's name); a boss shown under a reference's name gets its encounter ID from `Journal:ResolveID`. The Next spell alert shows a note line's spell name, as before, and any other line's own text.

**Phase events.** `CRT.db.alerts.phases[encounterID][ph] = { kind, value }` on top of `CRT.AlertPhaseDB`: a boss emote containing text, `UNIT_TARGETABLE_CHANGED` for a boss unit (read through `UnitCanAttack`), or a new boss unit (`INSTANCE_ENCOUNTER_ENGAGE_UNIT`). Values the game hides never match. `CRT_Dev/Dev/TimelineProbe.lua` logs these events on a real boss so a shipped trigger is added only once the values are readable.

**Alert areas.** `Areas.New(def)` in `CRT_Modules/Alerts/Areas.lua` makes a movable area from a definition: its key, the output it shows (`text`, `icon`, `circle` or `bar`), its layer, default position, a `make` that builds one pooled widget, a `draw` that shows one line on it, a `sample` for Previews and its own settings rows. The builder gives every area the same behaviour. It shows the soonest lines first, up to a cap of 1 to 10, the rest after the first in the grow direction (down, up, left or right). It pools widgets, so nothing is created per refresh. One 0.1 second ticker redraws every area, and only while a run, a preview or a test is going. A drag box with the area's name, a gear button and a reset button shows with Previews, and a locked area lets clicks through. The gear opens Raid Notes, Alerts tab, on that area (the settings are no longer a window of their own). While Previews are on, the gear also moves the main window to the screen side away from the area, for that session only, and it goes back to its saved place when Previews turn off (a window the player dragged meanwhile stays; the saved position is never changed). Each area registers a layer (`alerticons`, `alerttexts`, `alertcircles` beside `alertbars`) and a preview, and is reset by `Dev:ResetAllPositions`. A line glows (a pulsing border on the widget's own frame, never the game's) when its `glow` is on and its time has come. Whatever a line shows (text, spell name, icon, colour) goes through `readable`, so a hidden spell name or icon falls back to the alert's own text and no icon. The areas are `Texts.lua` (big text with the seconds after it, then NOW), `Icons.lua` (the icon with a countdown swipe, the seconds in its middle and the text beside it), `Circles.lua` (a ring that empties, the seconds inside and the text under it) and `Bars.lua` (the Stage 1 bars, with settings moved into its gear). Icons and circles use a `Cooldown` frame with the game's numbers, edge and flash off. The Cooldown is parented to a frame exactly the icon's (or ring's) size, because `CooldownFrameTemplate` anchors itself to its parent with `setAllPoints`, which would otherwise stretch the swipe over the whole row. The icon fades to grey as its time runs out (`Texture:SetDesaturation`, the Icons `fade` setting, on by default). The circles are a ring with a see-through centre: the swipe and a faint full ring behind it are one of three shipped textures in `CRT_Media/Media/` (`RingThin.tga`, `RingMedium.tga` and `RingThick.tga`, 256 x 256, 32-bit uncompressed, chosen by the `thickness` setting), and a new `Media` file is only seen after a full client restart. Circles start centred on the character. **Colours (2026-10-21):** every alert is drawn in its ability type's colour (`Reference.TYPES`, the Timeline's types, built from the one table `Reference.ABILITY_TYPES` at the top of `CRT_Modules/Timeline/Reference.lua`; the theme's `accent` with no known type). The Mech Alerts list draws each ability's name in its main type's colour and lists all its types on hover, through `Colors.Types(encounterID, bossName, difficultyName)`, which reads the boss once for the whole list. `CRT_Modules/Alerts/Colors.lua` (`CRT.AlertColors`) finds the type through one accessor, `Colors.TypeOf(encounterID, spellID, text, bossName, difficultyName)`: your own label for the ability on the Timeline, else the boss's ability timeline row (by spell, else by name, as reminders find their times; the difficulty's own timelines first) and its first type, else the first of the spell's Journal icons that is a type (`Reference.TAG_TYPES`, shared with the Journal export), from rows already read this session only (`Journal:CachedRows`): the Journal is never walked at a pull, when combat may not be set yet. `Colors.Stamp` reads the boss's references and cached rows once per run. `Alerts:Start` stamps it on each item as `abilityType` (`Colors.Stamp`); the boss's name for a timeline without an `Encounter:` line comes from `ENCOUNTER_START` (`run.bossName`, when readable), or in a rehearsal from the shown timeline's boss. The areas draw through `Areas.DrawColor(line, custom)`: the line's own colour when `Alerts:OwnColor` allows it (a raid note line's always, it is the raid leader's; any other, yours, only with Use custom colours on), else the area's own colour (bar colour, ring colour) with Use custom colours on, else the type colour. Use custom colours is `alerts.customColors` (off by default), a checkbox under Colours on the Alerts tab; off, the areas' colour rows, the Mech Alerts panel's Color and the editor's Color on an Only me alert are greyed and ignored, and what is saved stays. The Next spell alert follows the same rule (its own colour when allowed, else its type's), and keeps the heading colour when the type is unknown. An open alert editor greys its Color row as soon as the box changes (it listens to `Alerts:OnChange`). An ability timeline row's own `color rrggbb` is drawn only with it on too (`Reference.RowColor`). A swipe or bar starts full: its length is the time left when the line first showed, at most the alert's `warn` (a bar's `ahead`). The circle ring's direction is the `REVERSE` constant at the top of `Circles.lua`. Each area's settings are drawn by `Areas.Panel` into the Alerts tab: the rows the area asks for (`panel:Dropdown`, `Slider`, `Check`, and `Color`, a swatch that opens the game's `ColorPickerFrame` with opacity) under the common Show these alerts, how many at once and grow rows. The Alerts tab has a Configuration column with a dropdown of Icons, Texts, Bars and Circles, and a column of where your note lines go with Previews and Test all areas under it. Bars have a font, bar, background and text colours.

**The alert timeline (2026-10-21, phase 1).** `CRT_Modules/Alerts/TimelineArea.lua` (`CRT.AlertTimeline`, key and output `timeline`, layer `alerttimeline`, settings `alerts.areas.timeline`) is a fifth area in the style of the game's boss timeline, but CRT's own: it never touches the game's timeline frames (hooking into or replacing them is phase 2, waiting on research and Alex). It uses two optional def fields of `Areas.New`: `layout(area, n, now, s)`, which places the pooled widgets itself instead of the grow chain and gives the area's size (the line's box, centred on the saved position), and `noGrow`, which hides the Grow row. Each alert's icon (a 1 px edge in its type colour, white in the last 3 seconds; the countdown on it; the name and up to four Journal icons beside it) slides along a thin line toward its end, from `seconds` out to 0, over `length` px, in the chosen `direction`; tick marks (`ticks`, a text list of seconds, a shipped `CRT_Media/Media/Diamond.tga`, 32 x 32 like the rings) sit on the line with their seconds on the side away from the names. At 0 it plays its NOW effect for `nowTime` seconds (`flash`, `ring` with `RingThin.tga`, `pop` with the `nowText`, `slide`, or `none`). Icons that would overlap move to a second lane beside the line (`stack`). The 0.1 s ticker draws the lines; between those, one `OnUpdate` on the area's own mover frame moves them, set only while an icon is on the line. Its lines come from `outputs.timeline` (a Show as box in the editor and Mech Alerts, `show:timeline` on a note line, and `alerts.noteLines.timeline` for note lines without `show:`), from `seconds` before 0 until the NOW effect ends. The Journal icons are `item.abilityTags`, stamped by `Colors.Stamp` at the pull from the ability timeline row's `tags`, else the cached Journal row's (never a Journal walk). The area's many rows sit in the Alerts tab's `CowfeeRaidToolsAlertSettingsScroll`, whose bar shows only when the rows are taller than the tab.

**Note-line fields.** `CRT_Modules/Notes/Parse.lua` reads optional fields on a timed note line beside `dur:` and `colors:`: `show:` (a comma list of `alert`, `text`, `icon`, `bar`, `circle`, `timeline`), `tts:1`, `count:1`, `sound:<key>`, `glow:1`, `warn:<s>`, `linger:<s>` and `icon:<id>`, for example `time:1:20;ph:1;tag:DEATHKNIGHT;spellid:64843;text:Stack on X;show:text,icon,bar;tts:1;count:1;warn:8;linger:3;`. A line without `show:` behaves exactly as before, and `DisplayType` is still ignored. A line with `show:` uses only the displays it names, for whoever it is for, with its `text:` as the label and the spell giving the icon; the player's own switches (the Next spell alert, speech, bars, each area's Show) still apply when it is shown. `NoteEngine.ItemFor` builds the note block's item for a timer and is also used by the editor's Test. A tag can also be a class: the editor writes the class file name, such as `DEATHKNIGHT`, and `IsMine` matches it case-insensitively, with spaces removed, against both the localized class name and the file name, so any client language matches. A class word counts only for timed lines, so the assignments window is unchanged. `tag:everyone;` is a line for everyone, and a timed line with no tag alerts no one. `Parser.UnknownFields(line)` returns the fields the writer does not know, so rewriting a line keeps them.

**The alert editor.** `CRT_Modules/Alerts/Editor.lua` is one popout window for every alert, a line of a boss's raid note or one of your own reminders. It opens from a double-click on the Timeline and from a marker. The Mech Alerts tab edits your reminders in a panel of its own instead, through the same draft (`CRT_Modules/Alerts/Draft.lua`), saving each change at once, and uses the editor's Test and Save as template. It edits a draft (Save as, For, Difficulty, Relative to, Time, Show from, Linger, Icon, Text, Color, Show as, and speak, count down, glow and sound) and has Test, Export, Delete, Cancel and Save. A note line is written with `Notes:AddLine`, `ReplaceLine` or `RemoveLine`, each through `Parser.FormatLine`, and an edit always passes the raw line it read, so a note changed elsewhere is never overwritten. A new line goes where the pull will read it: the boss's note for that difficulty, else the boss's other note, and a new note only when the boss has none; the window says which with a "Saves to" line. A reminder with several times, saved as a raid note, writes one line per time. A line that had no `show:` gets explicit `show:`, `tts:` and `warn:` from what the editor shows, only when it is saved. Test builds its items in a block of its own (`minetest`) that gives them out only to a test run, so nothing is saved and no real pull is touched. Export shows the line in a copy box. The window follows the Modern and Classic look through `UI:StyleWindow`, and its For and Sound menus scroll when they are long (`maxHeight` on `UI.Dropdown`).

**Notes on the Timeline.** `CRT_Modules/Timeline/View.lua` opens the editor on a double-click on the Review track, anywhere, on a blank alert at that time (a double-click on a boss ability's icon also gives its spell). The editor and the game popups it opens sit above every window (FULLSCREEN_DIALOG). The time becomes a phase and seconds through the reference's numbered phase lines, and is shown back in tenths. Every timed line of the boss's raid notes and every time of your reminders is drawn as a small flag at its time, on its ability's row or on a Notes row, raid note lines and your reminders in different colours. Hovering a flag shows its text, who it is for, its phase and time and where it is saved, and a double-click opens it in the editor. On a recorded pull only phase 1 can be placed. Until the Timeline has a difficulty split the flags show every difficulty's note.

**Moving and Alt+drag.** Dragging a flag (its 20 px square at the head) moves its alert to a new time; holding Alt when the mouse button is let go adds another time instead. The drag keeps a copy of the mark it grabbed, so a redraw in the middle (flags come from a pool) cannot hand the drag to another alert. A reminder's time is changed with `Reminders:SetTime` or `AddTime`, which save its times as typed text, so a reminder that followed the reference now keeps its own list. A raid note line is moved with `Notes:ReplaceLine` and Alt+dragged with `Notes:AddLineTo` (an identical new line at the end of the same note), both only if the line is still the raw line that was drawn (`Notes:RawLines`); otherwise the view says nothing was moved. A drag let go off the track, or over the open alert editor, is cancelled.

**Saved alerts.** `CRT_Modules/Alerts/Saved.lua` (`CRT.AlertSaved`) keeps one alert's setup without its time in `CRT.db.alerts.saved[id]` (ids from `alerts.nextSavedId`): name, Save as, For words, spell, icon ID, text, colour, how it shows, speech, sound, glow, show-from and linger. `Save`, `Rename` and `Delete` tell the alerts windows and the store's own listeners (`OnChange`). The editor makes one with Save as saved alert (a name popup), opens one with `Editor:EditSaved(id)` (no time, difficulty, Export or Save as saved alert; Save overwrites it) and starts a new alert from one with `Editor:Open(..., prefill.saved)`. `CRT_Modules/Timeline/View.lua` shows them as chips in a strip under the lanes; a chip is dragged onto the track to place it (dropped on a cast icon it takes that icon's spell), and a right-click on a chip opens Edit, Rename and Delete. A right-click on the track that moves under 6 px and lasts under 0.3 s opens a menu (New alert here, Place and the saved alerts) through `MenuUtil.CreateContextMenu`; a longer one is the sideways scroll. The rename popup and the delete question are game popups lifted over the editor with `UI.LiftOver`, `UI.ShownPopup` and `UI.PopupEditBox` in `CRT_Core/UI/Panel.lua`.

**Saved data.** `CRT.defaults.alerts` in `CRT_Core/Core.lua`: `bars = { shown, noteLines, cap, ahead, width, height, font, fontSize, barColor, bgColor, textColor }` (and `position` once moved), `areas = { icons, texts, circles, timeline }` (each with shown, cap, grow, its size, font, font size and outline, `align` for texts, `fade` for icons, `thickness` and `ringColor` for circles; the timeline's own fields instead of grow: `direction`, `side`, `length`, `seconds`, `size`, `thickness`, `showNames`, `showCountdown`, `tenths`, `badges`, `ticks`, `nowEffect`, `nowText`, `nowTime`, `stack`, and `lineColor` once picked; `position` once moved), `noteLines = { text, icon, circle, timeline }` (where the player's own note lines also show), `customColors` (Use custom colours, off), `speechNotice` (the one-time login line has been shown), `reminders` (each now also with the `text`, `icon`, `circle` and `timeline` outputs and `linger`, `sound`, `glow`, `iconID` and `color` beside `outputs`, `speech` and `warn`), `phases`, `overrides` (empty) and `nextId`. Because `CRT_Core/Profiles.lua` reads the defaults, profiles carry it. Settings are read from `CRT.db.alerts` on every use, so a profile switch or reset in the middle of a pull is safe. See the maintenance skill's `references/alerts.md`.

## Sound

`CRT_Core/Sound/Engine.lua` (`CRT.Sound`) is the one way the addon plays or speaks. A sound is a reference string: `kit:<SOUNDKIT name or id>`, `lsm:<name>` (a sound another addon shares through LibSharedMedia-3.0, never shipped), `crt:<name>` (sounds shipped with the addon, `Sound.BUNDLED`, none yet: only audio made or licensed for the addon may go there), `file:<name>` (your own file) or `tts:<text>`. `Sound.Normalize` reads older saved values (a bare kit name such as `RAID_WARNING`, `none`), and `Sound.Compact` writes a game sound back bare, which is how note lines carry it so older versions and other raiders still read it. `Play(ref, opts)` returns the game's handle or nil (with what it tried), on the General Settings channel unless `opts.channel`; `Speak(text, opts)` uses the game's chosen voice checked once against `C_VoiceChat.GetTtsVoices()` and passes a secret text on untouched; `PlayOrSpeak(ref, text)` speaks when the sound didn't play; `Choices(opts)` is every sound dropdown's list (game sounds, the addon's own, shared, yours). `UI.SoundDropdown` (in `CRT_Core/UI/Controls.lua`) is the shared dropdown with a Play button per sound, used by the alert editor and Mech Alerts. Alert speech and sound cues (`CRT_Modules/Alerts/Speech.lua`), the break timer and `CRT:PlaySound` go through the engine; the low-health sound takes its list and file paths from it but keeps its own playing, which needs a volume, a repeat and the game's pulse.

**Your files.** The game can't list a folder, so a file is known by name: from the companion addon `CowfeeRaidTools_Media` (its `Sounds.lua` sets `CowfeeRaidTools_Media_Sounds = { "airhorn.ogg", ... }`, read at login) or typed on Quality of Life > Sounds (`CRTDB.sound.custom`, where the low-health page's old `customSounds` were moved). A `file:` sound tries `Interface\AddOns\CowfeeRaidTools_Media\Sounds\`, then the old `CowfeeRaidTools\CRT_Media\Sounds\`. The top-level `CowfeeRaidTools\Sounds\` from before the CRT_Media move is no longer read. Every file is registered in LibSharedMedia as `CRT: <name>` when another addon loaded it. The Sounds tab lists the files with a Test each (played or not found). The companion addon is shipped as a template inside this addon (`CRT_Media\Media Addon Template\CowfeeRaidTools_Media`), which the user copies into `Interface\AddOns` once, rather than as a second folder in the release: a packaged folder would be replaced by every update, removing the user's files, which is the problem it exists to solve. Whether a file copied in while the game runs is found after a /reload or only after a restart is to be checked in game; until then the texts say a restart may be needed.

**Aura sounds.** `CRT_Core/Sound/Auras.lua` (`CRT.SoundAuras`) wraps `C_UnitAuras.AddAuraSound(trigger, { unitToken, spellID, soundFileName, outputChannel, throttleSeconds })` and `RemoveAuraSound(id)` as `CRT.Sound:AddAuraSound(key, spellID, ref, { unit, trigger = "added" | "stacks" | "removed", throttle })` and `:RemoveAuraSound(key)`. The game plays these itself, so they work in combat and for private boss auras. The throttle is clamped to 0 to 5 seconds. The game's registrations are rebuilt from the wanted list as a whole, only out of combat with no encounter running; a change meanwhile waits for `PLAYER_REGEN_ENABLED` or `ENCOUNTER_END`. A file is passed as `soundFileName`; a game sound as `soundKitID`, which isn't confirmed. The first user is a Mech Alerts reminder with "Also when it lands on me" ticked (`r.auraSound`). `/crt dev sound <ref>`, `list` and `auras` (`CRT_Dev/Dev/Sound.lua`, developer builds only) test it all.

## Late tracker

`CRT_Modules/Late/Data.lua` keeps the schedule and the expected Raid Groups layout in `CRTDB.late`, starts a raid night from the schedule (a 5-second ticker) or from Start raid now, marks players as joined on `GROUP_ROSTER_UPDATE`, ends the night when the group disbands, on End raid or after 8 hours, and adds up the totals. `CRT_Modules/Late/Page.lua` is the Late Tracker page. The running night is stored in saved variables, so a reload does not lose it. See the maintenance skill's `references/late.md`.

## Tattlebot

`CRT_Modules/Tattlebot/Database.lua` is the shipped list of tracked boss mechanics, `CRT.TattleDB.bosses`, each boss with `mechanics = { { name, spells = { IDs } } }`. Players add their own in `CRTDB.tattle.custom[spellID]`, a mechanic name or `{ name, boss, encounterID }` when added from the Mechanics tab's Last fight view, which lists `Tattle:Scan()` with check boxes. `Tattle.LastFightBoss()` says whether the meter's current session is the last boss fight, by counting combat starts since `ENCOUNTER_END`. When that fight is the pull Tattlebot saved (`Tattle.LastFightPull()`), Add checked also writes the added spells' per-player damage from the scan into that pull (`Tattle:Backfill`). With no saved pull, `Tattle:AddScannedPull` saves the scanned fight as a pull (named "Not a boss" when it wasn't one) and keeps it linked to the scan for later adds. `Tattle.List()` maps every tracked spell ID to its mechanic. Pulls store damage per spell ID for every spell (`pull.all`, with the meter's avoidable spells in `pull.avoidable`), and the reports count only the tracked ones (`Tattle.Counts`), adding the IDs of one mechanic together (`Tattle.ByMechanic`) and counting a mechanic once per pull. So a mechanic added later counts on earlier pulls too. `CRT_Modules/Tattlebot/Data.lua` waits for `ENCOUNTER_END`, then for `PLAYER_REGEN_ENABLED` if still in combat, and one second later reads `C_DamageMeter.GetCombatSessionFromType(Current, DamageTaken)` and, per player, `GetCombatSessionSourceFromType` for their spells. It keeps only the listed spells, plus the meter's `AvoidableDamageTaken` spells when that setting is on. The meter is secret in combat, so a read that meets a secret is tried again up to 5 times. Players are named by matching the meter's GUID to the group, then by the meter's name. Pulls go into a night in `CRTDB.tattle.current`, which moves to `history` on End night or when the next pull is more than 6 hours later. Each night is filed under `CRTDB.tattle.season` when it starts (`night.season`; older nights count as "Season 1"). History's Season dropdown is All seasons (every saved night) or Current night (the running night, else the last saved one), and the Mechanic dropdown can narrow `Tattle.Summary(nights, mechKey)` to one mechanic, which then counts only pulls on that mechanic's boss, matched by the list's optional `encounterID` or by name. Chat posts go through `CRT.RaidReport:Output`. `CRT_Modules/Tattlebot/Page.lua` is the page, with Tonight, History, Mechanics (a boss dropdown, the list, and adding your own spell IDs) and Settings tabs. See the maintenance skill's `references/tattlebot.md`.

## Loot History

`CRT_Modules/Loot/Store.lua` (`CRT.Loot`), `CRT_Modules/Loot/Capture.lua`, `CRT_Modules/Loot/RCLC.lua` and `CRT_Modules/Loot/Page.lua` load after Tattlebot; the page registers as `loot` in the Late Tracker and Tattlebot block, and `/crt loot` opens it. Settings are in `CRTDB.loot` (`minQuality` 4, `dungeons`, `keepMonths` 12, `rcEnrich`); the records are in their own saved variable, `CRTLootDB`, so `CRTDB` stays small: `version` (the schema, with `MIGRATIONS` for the steps), `players` and `instances` (names kept once, records hold their index), `bosses[encounterID]` (the name from `ENCOUNTER_START` or `BOSS_KILL`) and `months["2026-10"]` (records in the order added). A record is an array, its fields named by `Loot.R`: `{ time, encounterID, instanceIdx, difficultyID, playerIdx, classID, quantity, itemString, rollType, lootListID }`, with the `item:` string, not the link. `Loot:Fire(what, record, month)` tells listeners `added`, `changed` or `reset`. Keep months prunes at login; delete one item (right-click on History), months before one, or all, then `Compact` drops unused names.

**Capture.** `ENCOUNTER_LOOT_RECEIVED` adds an item; `LOOT_HISTORY_UPDATE_DROP` reads the drop from `C_LootHistory.GetSortedDropsForEncounter` and, once it has a winner, updates that item's winner, class, roll (the winner's `rollInfos` state, or `playerRollState` when you won) and loot list ID in place. Items are matched by `encounter-difficulty-lootListID`, else by encounter, difficulty and item ID to a record still waiting (30 minutes), so either event may come first. Only raids, and dungeons with the setting; an item below `minQuality` is left out once `Item:ContinueOnItemLoad` has its quality; secret values are skipped. Each player records their own copy; nothing is sent.

**RCLootCouncil**, read only (`CRT_Modules/Loot/RCLC.lua`, to be removed once Loot Master handles loot itself): `RCLootCouncilLootDB.factionrealm["<Faction> - <Realm>"][winner] = { entry, ... }`, every field listed in the `WIRE` block at the top of the file. `RC.ParseTime` reads both date formats RCLootCouncil has used (`YYYY/MM/DD`, and `DD/MM/YY` in older data). Each award is read into one shape (response, colour, votes, note, roll, item level, owner, instance, the gear replaced, and `candidates` from `sessionResponses`, named through `RC:ResponseName`, which learns response numbers from the awards themselves). An award matching a record (same winner and item ID within 4 hours) goes in `Loot.rc[record]`; the rest go in `RC.unmatched`, newest first. Nothing is saved: a scan runs at login, a minute after new loot, and with Re-scan. Test: `run_loot_rclc.js` in the harness folder.

**The page.** History is a `WowScrollBoxList` with `CreateScrollBoxListLinearView` and `ScrollUtil.InitScrollBoxListWithScrollBar`, so only the visible rows exist; new loot is inserted into the data provider, a change re-initialises the visible rows, and a filter change or delete builds a new provider. A list entry is `{ rec, month }` or `{ award, month }` (an RCLootCouncil award on its own), and `fieldsOf(entry)` reads either into the same fields for the list, filters, summary and export. Columns: date, player, item, boss, difficulty, roll or response, votes, note, and Had (icons of the gear replaced); the tooltip adds every candidate. Filters are dropdowns (player, boss, difficulty, month, roll, and Source: recorded by CRT or RCLootCouncil only) built from the records, plus a search over lowercase item, player and boss names (cached per record, the item's name once the game has loaded it). Export CSV gives the filtered view in the copy box, with date, time, player, class, item ID and name, boss, instance, difficulty, roll, source, and the RCLootCouncil response, votes, roll, item level, note, gear replaced and candidate count. Summary counts each player's items and tier tokens (items the game files as Miscellaneous, Junk) in the same view. `/crt dev loot add`, `fill`, `stats` and `rc` (`CRT_Dev/Dev/Loot.lua`, developer builds only).

## Gear engine

`CRT_Core/Gear.lua` (`CRT.Gear`, loaded after `Themes.lua`, before any module) is the one source of truth for equipped gear. No module reads equipped items on its own; it asks the engine. The engine knows no feature. A piece is `{ slot, id, itemString, link, ilvl }`: `slot` an inventory slot id, `itemString` the link's `item:...` part with its empty tail dropped (bonus IDs, gems, enchant and crafter kept, at most `Gear.ITEM_STRING_MAX` bytes), `link` only on your own pieces, `ilvl` the item level with upgrades.

- **Slots.** `Gear.SLOTS` lists the worn-gear slots (`{ id, key, name }`, the shirt and tabard left out; `name` is the game's `HEADSLOT`-style string). `Gear.EQUIP_LOCS` maps an equip location to its slots, and `Gear.SLOTS_FOR(equipLoc)` returns a copy. `LM.SLOTS` is an alias of `Gear.EQUIP_LOCS` for older callers.
- **Yours.** `Gear:Mine(slot)`, `Gear:MineAll()` and `Gear:ForItem(itemString)` (your pieces in that item's slots, lowest item level first) read a cache. It fills on first use and on `PLAYER_ENTERING_WORLD`, refreshes one slot on `PLAYER_EQUIPMENT_CHANGED`, and reads a slot again on `ITEM_DATA_LOAD_RESULT` when its item level wasn't loaded (asked with `C_Item.RequestLoadItemDataByID`). Every game call is in pcall and a secret value reads as empty. `Gear:OnChange(fn)` calls `fn(slot)` when a slot's piece changes. `LM:MyGear` is a thin call to `ForItem`.
- **Other players.** `Gear:Remember(player, pieces, source, replace)` keeps pieces by full Name-Realm and slot, with `time()` and the source (such as `"lootmaster"`); with `replace` the pieces are the player's whole set, so a slot left out is empty (an inspect, a Gear Checker reply). `Gear:Of(player, slot)`, `Gear:OfAll(player)` (every piece, in slot order) and `Gear:When(player)` read them back. `Gear:ReadUnit(unit)` reads another unit's worn items now (an inspected player, after `INSPECT_READY`) and counts the slots whose link the game hasn't loaded yet. Memory only; a CRTDB table would plug in at `Remember` (a comment marks the spot).
- **What an item holds.** `Gear.Parts(itemString)` reads the enchant and gem IDs from the item string's fields (the wiki's ItemLink order: `item:itemID:enchantID:gem1:gem2:gem3:gem4:...`), `Gear.Sockets(itemString)` asks `C_Item.GetItemNumSockets` (what Blizzard's own inspect frame calls on an inspected player's link), `Gear.IsWeapon(equipLoc)` and `Gear.EquipLoc(piece)` tell a weapon, and `Gear.AverageLevel(pieces)` is the equipped item level over the 16 slots, a two-hander with an empty off hand counting twice.
- **Wire format.** `Gear.Encode(piece)` gives `"<slot>~<itemString>~<ilvl>"` (ilvl empty when unknown) and `Gear.Decode(text)` gives `{ slot, id, itemString, ilvl }`; both refuse junk and secret values. `Gear.PackMany(pieces, budget)` returns chunks of encoded texts, each within `budget` bytes joined with one-byte separators, and the pieces left out. One piece is at most 238 bytes, so it always fits a message.
- **Display.** `Gear.ShowTooltip(owner, piece, anchor)` shows the exact item with `SetHyperlink` on the item string when there is one, else `SetItemByID`, then "Equipped at item level N".

A new feature that needs gear: read your own with `Mine`/`ForItem`/`MineAll` and listen with `OnChange`; to share it, send `Encode`d pieces chunked by `PackMany` under your message's own head, `Decode` them on arrival and `Remember` them with your source name; show any piece with `ShowTooltip`. Tests: `run_gear.js`.

**Loot Master's G part.** After every answer (`R`, still carrying `id:ilvl` per piece) a raider's CRT sends `G|<sessionId>:<itemIndex>|<piece>;<piece>` on the Loot Master prefix through the same queue: `Gear.PackMany` with a budget of 255 minus the head, then `Wire.Pack`, so each message is 255 bytes or less (worst case exactly 255: an 8-character session id, a one-digit item index, a 238-byte piece). The looter and every raider window merge it with `Session:MergeGear`, which fills only the sender's own existing answer for that session and item, matching pieces by item ID (the same item level first), and then `Gear:Remember(sender, pieces, "lootmaster")`. A looter older than 0.30.0 drops the unknown kind; a raider older than 0.30.0 sends none, and its icons keep the tooltip by item ID. Tests: `run_lootmaster_gear.js` (with `CRT_Dev/Tests/old_Comm.lua`, 1.1.0's Comm frozen).

## Gear Checker

`CRT_Modules/GearChecker/` (`CRT.GearChecker`, loaded after Tattlebot, page key `gearcheck` in the Raid Groups and Ready Check block of `UI.MENU_GROUPS`; `/crt gear`, `/crt gear pop`) shows every group member's equipped gear with what is missing. All gear comes through the gear engine: yours from `Gear:MineAll`, everyone else's from `Gear:OfAll` after a reply or an inspect handed it to `Gear:Remember(..., true)`.

- **Rules** (`Data.lua`, no frames). The season decides which slots take an enchant and where empty sockets count: `{ enchant, enchantWeaponOnly, sockets, checks }` in the season's `GearChecks.lua` (`Bosses:SeasonData(key, "gearChecks", ...)`; a `gearChecks` field in `Season.lua` still reads), through `CRT.Bosses:GearChecks()` (Midnight S1: head, shoulder, chest, legs, feet, both rings and both hands, the off hand only when it is a weapon; sockets everywhere, since the item's own socket count decides). `GC.CheckSlot` flags a missing enchant (the item string's enchant field is empty), empty sockets (`Gear.Sockets` minus the gems in the item string) and a low item (`GC.LOW_ILVL`, 12, or more under the player's average); a piece known only by ID (no item string, or a bare `item:<id>`, `GC.PartsOf`) is never flagged for enchant, gems or bonus IDs, and never makes a bonus ID `require` shortfall. `GC:Roster()` is the group with unit tokens, you first; `GC:Row(member)` checks every slot and counts the issues, and counts a player as seen only with a whole set (`GC.WHOLE_SETS`: a Gear Checker reply or an inspect, never Loot Master's few pieces); `GC.Passes(row, filter)` is the chips (Everyone, Only issues, Missing gems, Missing enchants, then one per season check, from `GC:Filters()`; saved in `CRTDB.gearChecker.filter`, and `GC:FilterKey` turns a check the season no longer has into Everyone), and `GC.CellShows(findings, filter)` which cells a row draws: all under Everyone, else only the cells with that issue. **Season checks** are the season's `checks` list, `{ key, label, help, kind, ids, severity, slots, require }`: `itemIds` (an item is one of ids), `bonusIds` (an item carries one as a bonus ID, from `Gear.Parts(...).bonusIds`), `enchantIds` (a slot's enchant is not one of ids), `missingBonus` (an item carries none); severity `bad`, `low` or `info`; `require` (item and bonus IDs only) makes fewer than N matching slots one row issue (`row.rowFindings`, `Pair: 1 of 2 worn`). `GC:Rules()` keeps only checks with a known kind, a unique key and at least one ID, so a check written before its IDs has no chip. Each trip counts in `row.checkHits[key]` (its chip); a `bad` or `low` one also counts in Issues and adds its label to the slot's words (`GC.Problems`, so chat) and its line to `GC.IssueLines`. An `info` one (`GC.IsNote`) is to know, not to fix: never in Issues, Only issues or chat, its label in `GC.Notes` (the cell's hover, blue) and its line in `GC.NoteLines`. **Upgrade tracks** are the season's `tracks` topic (`Tracks.lua`, `Bosses:Tracks()`): `{ default, list = { { key, label, letter, quality, color } } lowest first, bonus = { [bonus ID] = { track, rank, max } } }`; `GC:Tracks()` checks it (a track's colour is the game's colour for its item `quality` through the shared `Gear.QualityColor`, else its own `color`, `GC.TrackColor`), `GC.TrackOf(parts)` reads a piece's track from its bonus IDs only (never tooltip text; an ID-only piece has none), and `CheckSlot` keeps it as `r.track`. `GC:Row` counts `row.trackCounts` (`GC.TrackText`, the Tracks column, highest first: `3M 3H`; when they don't fit, `P.SetTracks` drops the lowest and adds a `+`, and the badge tooltip ends with every count, `GC.TrackCounts`) and marks pieces under `GC:BelowTrack()` (`CRTDB.gearChecker.belowTrack`, else the season's default) as `r.below`, counted in `row.below`: the Below chip (`GC.BELOW`, last, only once the bonus map has IDs) lists those rows and draws those cells; they are no issue, only `GC.NoteLines` lines (`Slot [item] ilvl - Champion 4/6`). `/crt dev gear` (`CRT_Dev/Dev/GearProbe.lua`) prints the IDs to fill a check with, and the track the map gives each item (or unknown). `GC.SlotLine` (shift-click: `[Name] Slot [item link] ilvl - missing ...`), `GC.WhisperLines`, `GC.RaidLines` and `GC.ChatBoxText` (as many lines as fit in 255 bytes, then `(+N more)`) write the chat text; `GC.Say(lines, chatType, target)` sends only from a click, each line at most 255 bytes (`GC.CapLine`: item links become their plain names, then the line is cut) and `GC.CHAT_GAP` (0.4 s) apart, through `C_ChatInfo.SendChatMessage` (else the global), and shows the lines to you with red error text while `C_ChatInfo.InChatMessagingLockdown` holds chat. No lines send nothing. A chat type the game takes only from a key press or click (`GC.NeedsHardware`: Say and Yell in the open world, anything but a dungeon, raid, battleground, arena or scenario; a channel always) can't take the spaced lines, so `GC.Say` puts them all, joined, into a new chat box after `/s` (`GC.OpenChat`), for the player to send with Enter. A low item reads `N item levels under average`. `GC.IssueLines(row)` is the issues badge's tooltip (a line per issue, `bad` or `low`; nil not seen). `GC.SendTargets(row)` is where the menu can send: the group channel, Guild (`IsInGuild` and `C_GuildInfo.CanSpeakInGuildChat`), Officer (`GC.CanOfficer`: your rank's Officerchat Speak flag, `C_GuildInfo.GuildControlGetRankFlags(rank + 1)[4]`, as Loot Master reads it), a whisper (not your own row) and Say; `GC.Send(row, target)` sends the whisper lines to a whisper and the named lines anywhere else, through `GC.Say`.
- **Asking CRTs** (`Comm.lua`, prefix `CRTGearCheck`, `Comm.VERSION` 1). `Q|<version>|<request id>` asks the group; each CRT answers with its whole set, `G|<version>|<set id>|<part>|<parts>|<pieces>` (`Gear.PackMany` with room for the head, so every message is 255 bytes or less; a piece too long for a message on its own goes as `slot~item:<id>~ilvl`, so the set stays whole; fields after pieces are for later minor versions, and a higher major version is skipped). Everything goes to the group channel. A CRT answers only in a group, at most once per `REPLY_WINDOW` (10 s; asks in between get one answer when it ends, which reaches everyone), and an ask in combat is answered when combat ends. Sends wait a second on the throttle and hold during an encounter's lockdown, as Loot Master's do. A set is remembered once all its parts came; any message on the prefix marks its sender as having CRT (`Comm:HasCRT`, `Comm:Count` for the header's `Refresh (N/M have CRT)`). A CRT without the module never registers the prefix. `GC:Refresh()` asks, then after `REPLY_WAIT` (3 s) queues an inspect of everyone whose set didn't come; the page runs it the first time it shows and on Refresh.
- **Inspecting the rest** (`Inspect.lua`). One player at a time: never in combat (it waits for `PLAYER_REGEN_ENABLED`, and lets go of a player mid-inspect when combat starts, trying them again after), never while the game's own inspect window is open, and only when `UnitIsConnected`, `CanInspect` and `CheckInteractDistance(unit, 1)` say yes; a player out of range or offline is skipped (`Inspect.skipped`, shown as "not seen yet (out of range)") until the next Refresh. `NotifyInspect`, then `INSPECT_READY` with the player's GUID reads `Gear:ReadUnit` (again after `RETRY` while an item has no link or no item level yet), remembers the set as `"inspect"` and calls `ClearInspectPlayer`; `TIMEOUT` (5 s) moves on with no answer, and `DELAY` (1.5 s) separates two players; names queued while a timer waits go when it fires. A player whose CRT set arrived meanwhile is not inspected.
- **The page** (`Page.lua`). All 16 slots fit the page (`GC.PAGE_LAYOUT`: name 98, item level 40, issues 40, tracks 64, cells 47), so nothing scrolls sideways; the rows scroll down in a `WowScrollBoxList` with a skinned `MinimalScrollBar`, worked out once per change and repainted as they scroll. A cell is the icon in its quality's 1 px border, the item level under it, up to three gem diamonds in a column down its right edge (white squares turned 45 degrees: filled, or dark with a red edge), its track and rank at its top left (`GC.TrackTag`, `H4`, in the track's colour on a dark backing, at most `L.trackMaxW` wide so a larger font never reaches the diamonds) and, on a slot that takes an enchant, a dot at its bottom left (green, red when missing); a missing enchant or gem draws a red outline, a low item an orange one, and a season check a small square at the icon's bottom right in its severity's colour (`GC.TopCheck`; blue for info). The chips wrap onto another row past `L.chipsW` (600), moving the headings and list down. The Below chip is as wide as its longest label and has an arrow (and a right-click) that opens `P.OpenBelowMenu`, a `UI.ContextMenu` with a radio per track but the lowest; a pick is saved and turns the filter on. The chips are tab-styled buttons (`UI:RegisterTab`, `UI:StyleTab`). Text and rows read `CRT.PALETTE` in Modern and the game's gold and dark in Default: Blizzard, redrawn on `UI:OnTheme`; the data colours (red, orange, green, gem blue) are the same in every theme. The quality border is Uncommon until the item loads; `ITEM_DATA_LOAD_RESULT` for a shown item redraws the page once. Hover shows `Gear.ShowTooltip` and what is missing; shift-click on an issue puts its line in the chat box (`ChatFrameUtil.InsertLink` into the box being typed in, else `ChatFrameUtil.OpenChat`; the 11.x `ChatEdit_*` names are fallbacks); hovering the issues badge (a button the badge's size) shows the name in class colour and `GC.IssueLines`, else No issues or Not seen yet, then a Not an issue heading over `GC.NoteLines` (info checks in blue, below-track items in their track's colour); a right-click on a row, cell or badge opens `UI.ContextMenu` with a Send issues to submenu (`GC.SendTargets`; Say in the open world has a tooltip saying it goes to the chat box), Put in chat box and Inspect (`InspectUnit`, out of combat); with no issues the first two are greyed. Pop out reparents the page's body into `CowfeeRaidToolsGearCheckerWindow`, a `UI.Window` pop-out on the `popups` layer (at least 1024 wide, so a row always fits), as the Timeline does; its place and size are in `CRTDB.gearChecker.popout`, and closing it docks the body again.

Tests: `run_gearchecker_data.js` (rules, rows, filters, info checks, upgrade tracks and Below, chat text and sends, the inspect queue), `run_gearchecker_comm.js` (several CRTs and 1.1.0's frozen Loot Master Comm in one raid) and `run_gearchecker_page.js` (the page on the real UI helpers in each theme, the menu, the pop-out, issue-only cells, season-check chips, track tags, the Tracks column and the Below chip) and `run_gearprobe.js` (`/crt dev gear`).

## Loot Master: CRT Looting

`CRT_Modules/LootMaster/AutoPass.lua` is the auto-pass gate: `AutoPass:ShouldPass(state, roll)` is pure (no game calls, no globals) and returns true only when every check holds, else false and the first failing reason; a test is a no before anything else. `AutoPass:LeaderRoll(state, roll, info)` is the raid leader's pure gate (Need, else Greed, else Transmog, with the same boss and instance checks). It is the only file allowed to call `RollOnLoot` and `ConfirmLootRoll` (`AutoPass:Pass`, `:Roll`, `:Confirm`, each in pcall; the lint in `CRT_Dev/Tests/run_all.sh` fails the build otherwise; `CRT_Dev/Dev/LootProbe.lua` is exempt). `CRT_Modules/LootMaster/Rolls.lua` handles the game's roll events (`START_LOOT_ROLL`, `CANCEL_LOOT_ROLL`, `CANCEL_ALL_LOOT_ROLLS`, `CONFIRM_LOOT_ROLL`): a raider's pass straight away (a roll refused only for a late heartbeat is tried once more on the leader's next word while `GetLootRollTimeLeft` is above 0), the leader's roll and its confirm (only CRT's own call, within 3 s, not failed or kept open), the 3 s watch for the game closing the roll, and a chat line for each. The leader's boss rolls go on the Boss loot list, `CRT_Modules/LootMaster/BossLoot.lua` (no frames: rows pre-ticked by the loot filter, who won from `LOOT_HISTORY_UPDATE_DROP` with `C_LootHistory.GetSortedInfoForDrop` and from `ENCOUNTER_LOOT_RECEIVED`, `BL:Start` with the ticked rows you won, emptied on leaving the instance, CRT Looting off, and 10 minutes after the kill), shown in `CRT_Modules/LootMaster/BossLootWindow.lua` (a `UI.Window` pop-out, `/crt loot boss`). Nothing starts a session by itself. A roll is a boss's when it starts within `LM.BOSS_SECONDS` of a kill in the same instance (`LM:LastKill`, whose saved kill now keeps its instance key). `CRT_Modules/LootMaster/Looting.lua` keeps CRT Looting's on state in memory only (a login or `/reload` starts it off; a wipe keeps it on while the leader is in the open world, IsInInstance's `none`, for up to `LM.LOOTING_AWAY`, 10 minutes; any other instance turns it off), sends the leader's `O` (on), `F` (off, with why) and `H` (heartbeat every 30 s, with where the leader is) on the Loot Master prefix, takes them only from the current raid leader (forgetting them when the lead moves or the leader goes offline), refuses finder groups, and parties unless `CRTDB.lootmaster.enableInParty` is on, shows red error text (`LM.ShowError`) for a click during the chat lockdown, collects the gate's facts (`LM:LootingState`) and gives the one-line state (`LM:LootingStatus`). `CRT_Modules/LootMaster/LootingPrompt.lua` is the leader's "Use CRT Looting in this instance?" dialog. Tests: `run_lootmaster_autopass.js` (every combination of the checks, both gates), `run_lootmaster_looting.js`, `run_lootmaster_rolls.js` and `run_lootmaster_bosswin.js`.

## Loot Master: the loot filter

`CRT_Modules/LootMaster/Filter.lua` decides which items open a loot session; Loot History keeps its own `minQuality`. The setting is `CRTDB.lootmaster.filter` (`boss`, `trash`, `quality` from `LM.FILTER_QUALITIES`, `ilvl` with 0 for any, 0 to 500 in `LM.LIMITS.filterIlvl`, `kinds[key]` for each of `LM.FILTER_KINDS`), its defaults only in CRT_Core/Core.lua (`LM.FilterDefaults` copies them). `LM.ItemFacts(itemString, source)` reads the facts from the game (quality, item level, class and subclass, bindType, setID, toy, mount, pet, cosmetic, and tier: a Miscellaneous item with a Classes line, or gear with a setID and a Classes line, as no API says an item set is a class set; a token for every class has no Classes line and counts as other, which the Kinds help says) and lists in `facts.unreadable` what it couldn't read (the fact left nil; `facts.kindUnknown` when the kind can't be told); `LM.PassesFilter(facts, filter)` is pure; `LM.ItemKind` puts each item in one kind (toy, mount or pet, cosmetic, tier, then gear by binding, else other). A part whose fact can't be read is skipped and the item let through on it (Alex: "Let it through"); the readable parts still count, and `LM:FilterLoot` says in chat what it couldn't read for an item it lets through; the session start from real loot is to call it. `/crt loot test` shuffles the pool, reads it only until enough pass, picks those read in full before those let through, and says when it fills with others. The tab is `CRT_Modules/LootMaster/FilterTab.lua` (`LM.BuildFilterTab`, given the page's heading and check helpers), between Raider Score and Settings. Sync Master Loot sends the filter as its `F` part, counted by a field at the end of `H`; an older receiver drops both (`CRT_Dev/Tests/old_Sync.lua` keeps the 0.27 receiver to test that). Since 0.28 (`LM.FILTER_SYNC_SINCE`) the `K` answer carries the sender's `LM.VERSION`; the leader's status line lists those who answered with none or an older one as synced, but too old for the loot filter. Tests: `run_lootmaster_filter.js` and `run_lootmaster_sync.js`.

## Timeline

`CRT_Modules/Timeline/Data.lua` is the store and the recorder, `CRT_Modules/Timeline/Journal.lua` finds a boss's ability rows, `CRT_Modules/Timeline/Database.lua` holds the shipped reference texts, `CRT_Modules/Timeline/Reference.lua` reads and keeps reference timelines, `CRT_Modules/Timeline/Lanes.lua` builds the lanes, `CRT_Modules/Timeline/View.lua` draws a pull or a reference, `CRT_Modules/Timeline/ReferencePage.lua` is the References tab and the Recent pulls list, `CRT_Modules/Timeline/ReviewTab.lua` builds the Review tab's controls (the Difficulty, Boss and Pull dropdowns, the checkboxes, the zoom slider, the Recent pulls list and the view), `CRT_Modules/Timeline/SettingsTab.lua` builds the Settings tab, and `CRT_Modules/Timeline/Page.lua` is the page that holds the choices (difficulty, boss, pull, overlay) and wires the three tabs together. They load in that order (Data, Journal, Database, Reference, Lanes, View, ReferencePage, SettingsTab, ReviewTab, Page) after Tattlebot, and `CRT_Dev/Dev/TimelineProbe.lua` loads last inside the `.toc`'s do-not-package block. The pulls live in `CRTDB.timeline` (defaults in `CRT_Core/Core.lua`, so profiles carry it): `bosses[encounterID] = { name, pulls = { newest last } }`, where a pull is `{ id, encounterID, name, difficultyID, startedAt, length, kill, casts = { { t, dur, spellID or 0 } }, deaths = { { t, name, class, role, recapID, spellID or 0 } } }` with times in seconds from the pull start, rounded to 0.1. Alongside it are `rows[encounterID] = { hidden = { [spellID] = true }, custom = { spellID, ... } }` and the settings `record`, `minPull` (15), `keep` (10), `span`, `grid`, `iconSize`, `deathRows`, `roles`, `firstDeaths`, `overlay` (how many pulls), `overlayOn`, `hideEmpty` and `nextId`. `Timeline:SavePull` numbers a pull from `nextId` and drops the oldest past `keep` of its difficulty group for that boss (the other group's pulls are never dropped); `Timeline:Fire` tells the page (through `OnChange` listeners, each in a `pcall`) after any save or delete. Recording works like Tattlebot's read. `ENCOUNTER_START` in a raid instance (with Record on and a readable encounter ID) starts a pull; `ENCOUNTER_TIMELINE_EVENT_ADDED` notes each boss event (source Encounter) with its duration and spell ID, 0 when the spell is secret; `ENCOUNTER_TIMELINE_EVENT_STATE_CHANGED` turns an event into a cast, timed from the pull start, when `C_EncounterTimeline.GetEventState` says Finished, and drops it when Canceled; `_REMOVED` drops it too. `ENCOUNTER_END` ends the pull, and one shorter than `minPull` is dropped. If still in combat the pull waits for `PLAYER_REGEN_ENABLED`; then, `READ_DELAY` (1 second) later, `readDeaths` reads `C_DamageMeter.GetCombatSessionFromType(Current, Deaths)`: for each source its `deathRecapID`, name, `classFilename` and `deathTimeSeconds`, and the role matched from the group by GUID then name. The killing blow is the first readable spell of `C_DeathRecap.GetRecapEvents` (newest first), else the first meter spell with `isDeadly` from `GetCombatSessionSourceFromType`, else 0. A read that meets a secret name or time is tried again every `RETRY_DELAY` (2 seconds) up to `RETRIES` (5) times, and then saves what it has (a death with no time is listed as "time unknown"). The meter's current session turns into the next fight's when combat starts, so `PLAYER_REGEN_DISABLED` and a new `ENCOUNTER_START` save any pull still waiting at once, with the deaths of its last completed read. A `/reload` mid-pull loses that pull. Secret-value rules: every game call is in a `pcall`, and every value goes through `readable(v)` (`issecretvalue`) before it is compared, tested, added up, counted or used as a key; a secret spell ID records the cast as unnamed (0). `Journal:Rows(encounterID)` walks the boss's Encounter Journal sections (`EJ_GetInstanceForMap`, else `EJ_GetInstanceByIndex` over the current tier, `EJ_SelectInstance`, `EJ_GetEncounterInfoByIndex`, the dungeon encounter ID in the seventh return of `EJ_GetEncounterInfo`, `C_EncounterJournal.GetSectionInfo`), keeps each spell once, then adds your own rows. It runs only out of combat with the Journal window closed, puts back the selected instance, caches by boss, and remembers a miss until the zone changes. `Lanes.Build(base, rows, settings, encounterID, overlay)` builds the deaths row(s), the ability rows and a "Boss casts (unnamed)" row (only when it has casts) for a pull, and returns the lanes, the deaths with no time, and `extra` (`phases`, `length`, `endLine`); the deaths overlay uses `Timeline:RecentDeaths(encounterID, count, fromID)`. The page registers as `timeline` in `UI.MENU_GROUPS`, and `CRT_Core/Slash.lua` routes `/crt timeline` to it. `CRT_Dev/Dev/TimelineProbe.lua` (`CRT.TimelineProbe`) never ships. `/crt dev probe` arms it for the next raid boss pull, and for each timeline, boss cast, meter, recap and Journal field it logs whether the value was secret, readable, missing or an error, when the event fired, at `ENCOUNTER_END` and after combat; the counts go in `CRTDB.dev.probe` and `/crt dev probe show` prints them. See the maintenance skill's `references/timeline.md`.

**Minimize.** `UI:SetMinimized(on)` in `CRT_Core/UI/Panel.lua` shrinks the main window to its title bar (26 high), hiding the menu, the content and the template's inset, after pinning its top-left corner so it shrinks upwards. The minimize button (`f.minimizeButton`, a line or a small square drawn with textures, styled by `UI:StyleMinimizeButton` for each look) sits left of Previews, and an invisible `titleBar` button over the title bar moves the window on drag and toggles minimize on double-click. `UI:Show` always restores, so `/crt` restores a minimized window instead of closing it. The state is not saved.

**Difficulty groups.** The Timeline tells two groups apart, `"nh"` (Normal/Heroic) and `"mythic"`, named by `Timeline.GROUP_NAMES`. `Timeline.DifficultyGroup(difficultyID)` is `"mythic"` for difficulty 16 and `"nh"` for everything else, so a pull needs no new field. `Timeline:Bosses(group)` counts only that group's pulls (a boss with pulls only in the other group is still listed, with count 0), `Timeline:Pulls(encounterID, group)` and `Timeline:RecentDeaths(encounterID, count, fromID, group)` take the group as their last argument, and no group means every pull. A reference has a group too: `Reference.Group(ref)` is `"mythic"` for a `Difficulty: Mythic` line and `"nh"` for anything else or none, and `Reference:ForGroup(entries, group)` filters what `List` returns. `Reference.MythicOnly(row)` is true for a row whose types hold `mythic`. `Reference.StampDifficulty(text, group)` sets the text's Difficulty line (Mythic for `"mythic"`; for `"nh"` a Normal or Heroic line stays and anything else becomes Heroic; a text with no line gets one after the Boss line) and keeps every other line and each line's `
`. `Reference.CopyTo(text, group)` stamps the text for the group and, for `"nh"`, drops the Mythic-only ability lines (header, Phase and `#` lines stay), returning the text and how many lines it left out. `Lanes.Build(base, rows, settings, encounterID, overlay, group)` takes the group: on `"nh"` a reference row that is Mythic-only is left out with its casts, and the deaths overlay comes from that group's pulls. `Page.lua` keeps the group (it starts on `"nh"` each time and is not saved); the boss list, pull list, references list and Recent pulls list all filter by it. The References tab's Save runs `StampDifficulty` with the page's group (what is typed is parsed as typed, so an error names the right line), and each listed reference has a Copy to button that runs `CopyTo` for the other group and `Reference:Add`s the result. A reference listed for another group or boss is no longer edited; Save then adds a new one.

**Moving phase lines.** `Reference.Parse` reads `Phase: [label] time (planned time)` into `phases = { { t, planned, label } }`, `planned` being `t` when there is no `(planned ...)`. `Reference.MovePhaseText(text, index, t)` rewrites the index-th Phase line in time order (the `(planned ...)` goes away at the planned time), and `Reference:MovePhase(key, index, t)` saves it: a reference of your own is updated in place, a shipped one is `Add`ed as a copy of your own, and it returns the key and whether it is a copy. `Reference.PhaseStarts(ref)` is `{ 0, phase 1's start, ... }` for the alerts side. In `referenceLanes` each cast belongs to the phase it was planned in (by the planned times), moves by as much as that phase's line moved, and is hidden, never dropped from the reference, while it would land at or after the next phase's start; `extra.masked` counts those. In `View.lua`, `PhaseNear` finds a line within 4 px of the cursor, `PhaseMouseDown` starts a drag on Shift + left button (or arms a reset on a right-click of a moved line), `UpdatePhaseDrag` keeps the line 5 seconds from its neighbours and the pull and redraws, and `FinishPhaseDrag` and a short right-click call `view.onPhaseMoved(index, seconds)`, which `Page.lua` routes to `Reference:MovePhase` and prints a message when it made a copy. `CRT_Modules/Alerts/Reminders.PhaseCut(ref, ph)` is the same mask for the alerts: whatever a phase has timed at or after the earliest later phase line never comes.

**Pop-out window.** The Review tab's content is built in a frame of its own inside the tab, so Pop out can reparent it into `CowfeeRaidToolsTimelineWindow`, a resizable frame (at least 760 x 360) with a drag header, a `UI.ResetButton`, a size grip and the `timeline` layer. The tab then shows a "Bring it back" note. Closing the window by Dock, its X or Escape reparents the content back. The page's `refresh` also runs while only the window is shown. Size and position are saved in `CRTDB.timeline.popout`, and `/crt timeline pop` calls `CRT.TimelinePopout`.

**Reference timelines.** A reference is a boss's planned cast schedule, written as plain text and parsed by `Reference.Parse(text)` into `{ boss, difficulty, length, encounterID, phases = { { t, label } }, rows = { { name, spellID, color, lead, casts = { { t, dur } } } } }`, or `nil` and a list of `Line N: reason` errors. The text is one line per thing: `Boss:` (required), `Difficulty:`, `Length:`, `Encounter:`, `Phase: [label] time`, and any other line is `Name [spell N] (lead N, color rrggbb): time, time+bar, ...`. A time is `m:ss` or plain seconds; blank lines and `#` lines are skipped; curly apostrophes and stray spaces from pasted text are folded; without `Length:` the length is the last cast plus its bar. Shipped references are `[[ ]]` text blocks in `CRT.TimelineDB.references` (`CRT_Modules/Timeline/Database.lua`), and your own are saved as `{ id, text }` in `CRTDB.timeline.references` with `nextRef` as the next id (both defaults in `CRT_Core/Core.lua`, so profiles carry them; only the text is stored and it is parsed again when needed). `Reference:List()` returns yours first and then the shipped ones as `{ key, ref, own, text }`, the key being `own:<id>` or `ship:<index>`; `Find(key)`, `ForBoss(encounterID, name)` (by encounter ID when the reference has one, else by boss name) and `BossKey(entry, listed)` (the dropdown key of the listed boss it belongs to, else `ref:<name>`) say which belong to which boss; `Add`, `Update` and `Delete` change your own and call `Timeline:Fire()`, and a shipped one cannot be changed. `Label(ref)` is `Reference · Mythic · 9:48`. The page adds a boss that has only a reference to the dropdown by its `ref:` key, and keeps it selected by name when it gains a numeric key. `Lanes.Build` takes `base`, which is a recorded pull, or `{ reference = ref }`: for a reference it builds the deaths lane (from the overlay pull only), one `reference` lane per row in file order, and with an overlay pull a `ticks` lane `Pull N casts` of that pull's cast times; `extra.phases` is the reference's, `extra.length` the longer of the reference and the overlay pull, and `extra.endLine` the overlay pull's length. A row's spell is `Lanes.RowSpell(row, encounterID)`: its `[spell N]`, else the Journal row of the same name (trimmed, any case), else 0; the icon is that Journal row's, else `C_Spell.GetSpellTexture`, else a question mark. A row hidden by spell ID or by name (`rows[encounterID].hiddenNames`) is left out, and `deathRows` is honored for the overlay's deaths. `View` draws `reference` lanes with a bar behind each cast that has a duration, a thin lead line from `t - lead` to the icon, the row name in its color, and red phase lines with their labels; the overlay pull's end is a line. `ReferencePage.Build` is the References tab (a paste box with Save and a list of the selected boss's references with Edit, Delete and Copy) and `ReferencePage.Recent` is the Recent pulls list that sets the overlay pull, which is not saved. Journal reads for a reference use the reference's own `Encounter:` when the boss key is a string. Reference icons and spell tooltips depend on the Journal, which is read only out of combat.

**Rehearsal.** `CRT_Modules/Timeline/Rehearsal.lua` (`CRT.TimelineRehearsal`) has no frames. `NewClock()` turns `GetTime` into fight seconds (`Now`, `Play`, `Pause`, `Playing`, `Seek`, `SetSpeed`, `SetLength`): it plays at 1x, 2x or 4x, can jump, and holds at the fight's length. `Build(lanes, extra)` lays the fight out as `{ casts, phases, length }` from the `reference` and `spell` lanes only (a cast keeps its lane table, ties keep lane order); `CastAt(model, t)` is the fake cast bar (each cast shows for `CAST` = 5 seconds ending on its time, the one ending first wins), `NextUp(model, t, n, skip)` (leaving out the cast bar's cast) and `PhasesUpTo(model, t)`. `STRIP_SPAN` = 40 is the strip's width in seconds, "now" a third across. `CRT_Modules/Timeline/RehearsalWindow.lua` (`CRT.TimelineRehearsalWindow`) is the window: a boss frame with a health bar draining evenly over the length, the cast bar, Next up (the next 3 casts, without the one in the cast bar), the strip (a line every 30 seconds, the time over the now line; click to seek, or drag with either button to scrub, the clock jumping once on release), Play/Pause, Restart, a Speed dropdown and a Preview as dropdown. `Open(source)` builds the model with `Lanes.Build` on the same base, order and group as the Review tab, so moved phase lines and the chosen Order are played. The window only drives its own clock and calls hooks (`onPlay`, `onSeek`, `onAs`, `onTick`, `onClose`); `CRT.TimelineRehearsalRun`, at the end of the file, sets them. Preview as lists Me, Everyone, then `CRT.AlertRoster:Players()` (the selected Raid Groups layout, or the group). `Run.Play` calls `Alerts:Start(encounterID, difficultyName, "rehearsal", { clock, speed, as })` (`as` is nil for you, `"*"` or a player's name) and then starts every phase line at or before the clock; `Run.Tick` starts each phase line the clock passes with `Alerts:StartPhase(ph, "rehearsal", Alerts:TimeAt(t))`, the number taken from the line's label by `Reminders.PhaseNumber` (phase 1 and unnumbered lines start nothing). A seek, Restart or new Preview as is `Alerts:Stop(true)` and a fresh Start at the clock's time; Pause leaves the run going with the clock still. `Alerts:IsRehearsal()` tells a rehearsal run from a real one, and Play never replaces a real run. `Run.Blocked()` gives the reason Rehearse can't open (combat, a boss encounter, or a real run or test going), and `Run.OnChange(fn)` is told when combat or an encounter starts or ends. `PLAYER_REGEN_DISABLED` and `ENCOUNTER_START` close the window and stop a rehearsal run. The engine side (`CRT_Modules/Alerts/Engine.lua`, `CRT_Modules/Alerts/Roster.lua`) is the alerts code's: the run takes its time from `Alerts:Now()`, sends nothing and drops items due before the start. The entry points are in `CRT_Modules/Timeline/Page.lua`: the Rehearse button beside Pop out on the Review tab (greyed by `Blocked()`, and when nothing is shown), `Timeline:RehearsalSource()` (what the Review tab shows: `base`, `encounterID`, `group`, `order`, `bossName`, `difficultyName`) and `Timeline:Rehearse()`, which `/crt timeline rehearse` in `CRT_Core/Slash.lua` calls. The only saved field is `timeline.rehearsal = { point, x, y, speed, as }`, made when first needed; the clock and the source are not saved. The two files load right after `Lanes.lua`. Harnesses: `run_timeline_rehearsal.js` (clock and model) and `run_timeline_rehearsalwin.js` (window and run).

**Undo.** `CRT_Modules/Timeline/Undo.lua` (`CRT.TimelineUndo`) gives the timeline Ctrl+Z and Ctrl+Y (or Ctrl+Shift+Z), which `CRT_Modules/Timeline/View.lua` takes while a view shows. It does not follow actions: it keeps a copy of each note (`CRT.db.notes.list[id]`), each boss's reminders (`CRT.db.alerts.reminders[encounterID]`) and each own reference (`timeline.references`, by id), and on the Notes, Alerts and Timeline change events records the items that differ as one step (changes in one frame join one step), up to 30. Undo and Redo put back only a step's items and fire the three change events. An item changed while no view shows, or inside `Undo:Quietly` (a note received in `CRT_Modules/Notes/Comm.lua`), is dropped from the steps, so a later change made elsewhere is never overwritten. Each view registers its frame with `Undo:Watch`.

## Apply algorithm

`Apply:Start(slots)` runs only for a raid leader or assistant, in a raid, out of combat.

1. Read the raid and match layout names to members (`resolveLayout`).
2. Give every member a target group. Layout players go where the layout says. Everyone else keeps their group if there is room, otherwise takes the first free seat.
3. Take one step at a time. Pick a misplaced player, then either `SetRaidSubgroup` into a group with space or `SwapRaidSubgroup` with someone who does not belong there, preferring the person who wants the first player's group.
4. Wait for `GROUP_ROSTER_UPDATE`, re-read the raid, and take the next step.

Every step puts one more player in the right place and never disturbs a correct player, so it always finishes. Stop conditions are: combat starts, 150 steps, or three 1.5 second timeouts with no roster update. Players in combat are skipped and reported at the end.

## Export format

`CRT1;<name>;<slot1>,<slot2>,...,<slot40>`. The characters `%`, `;` and `,` inside values are written as `%XX`. No pipe character is used because the game treats `|` as an escape code in text. Import also accepts a plain list: one name per row, tab-separated columns use the first non-empty cell, blank rows leave a slot empty, and more than 40 rows is rejected.

## Fonts and layout

`CRT_Core/Core.lua` makes six font objects (`CRTFontNormal`, `CRTFontHighlight`, `CRTFontDisable`, `CRTFontSmall`, `CRTFontDisableSmall`, `CRTFontLarge`) by copying Blizzard's fonts and multiplying the size by `CRT.FONT_SCALE`, currently 1.2. All text uses these, so one number changes every font. Layout constants sit at the top of `Page.lua` and `Panel.lua` (`SLOT_W`, `SLOT_H`, `BLOCK_H`, `GRID_TOP`, `RIGHT_W`, `FRAME_W`, `FRAME_H`). Change fonts and sizes together, or text will not fit its slot.
